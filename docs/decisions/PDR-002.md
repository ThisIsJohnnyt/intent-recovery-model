# PDR-002: Sync the dataset curator via live GitHub read access, not manual relay

**Date**: 2026-07-29
**Status**: Accepted

## Decision

**Accepted**: ChatGPT (dataset curator) checks the actual current repo via its
GitHub connector's read access before proposing dataset/docs content, instead
of relying on a manually pasted file bundle or its own memory of prior
conversations.

**Rejected**: a proposed workflow where a dedicated `ai/gpt-claude-collab`
branch lets Claude Code "automatically" detect and review the curator's pull
requests in the background. Claude Code only acts when a session is
explicitly invoked and given a task — it does not run a standing process that
watches GitHub for new PRs. This is true regardless of what the curator's
GitHub connector can do, since it's a claim about Claude Code's behavior, not
the curator's.

**Rejected (tested)**: a branch/PR flow where the curator commits proposals
directly via its GitHub connector's write access. Tested 2026-07-29: the
connector recognized the repository and reported read access and repository
metadata access as working, and reported write permissions as present, but
the actual branch-creation write was blocked by OpenAI's own safety layer
before the request reached GitHub at all ("could not determine the request's
safety status") — no branch, commit, file, or PR was created. This is a
platform-level block, not a permissions or repo-configuration problem, so
retrying with different phrasing/scope isn't expected to help. The manual
relay process (product owner pastes the curator's output, Claude Code
reconciles and commits) remains the only working path for getting the
curator's content into the repo.

## Reasoning

Nearly every dataset-content conflict this project has hit so far — the
schema mismatch in the original `gold_v1.2` draft and again in a later
`dataset/schema.json` proposal, the diagnosis-framing wording recurring in a
curriculum doc, an imagined `dataset/`/`gold_v1.2/` package structure that
didn't match this repo, duplicate `CHANGELOG.md`/curriculum-spec/category-
reference proposals — trace back to one root cause: the curator proposing
content without visibility into actual repo state, not a lack of git
automation. A manually relayed file bundle (tried once, for `gold_v1.2`'s
Boundary Evidence reconciliation) fixes this only until the repo changes
again. Live read access through the GitHub connector fixes it directly and
stays current with no relay step.

Write access was granted at connector setup but hadn't been exercised at the
time this PDR was first drafted — only reads had been confirmed working.
Rather than adopt a commit-directly-to-a-branch workflow on the strength of an
untested grant, the product owner ran the cheap, reversible test this PDR
called for, and it settled the question directly: the write path is blocked
at the platform level, independent of repo permissions. A GitHub-API-based
connector should also only ever see what's actually been pushed —
`datasets/real_holdout.jsonl` is gitignored and has never reached GitHub, so
it stays unreachable regardless of any write grant, though this was reasoned
rather than separately tested (moot now that write access itself doesn't
function).

## Approach

1. Product owner tells ChatGPT (Project custom instructions, or pinned at the
   top of a working conversation) to check the live repo via the GitHub
   connector before proposing dataset/docs content — no code or repo change
   required for this part.
2. Continue the existing manual relay process for getting the curator's
   content into the repo: product owner pastes the curator's output, Claude
   Code reconciles it against actual repo state and commits. Revisit this PDR
   only if OpenAI's connector write path changes in a future update — no
   action needed on this repo's side until then.
